# LIVKA CONTROL — доступ и роли

## Как сейчас устроен вход

1. Зарегистрируйтесь на сайте как обычный пользователь (`/` → «Войти» → регистрация).
2. Выдайте себе роль `admin` вручную в базе данных (SQL ниже).
3. Откройте `/admin` и войдите тем же email и паролем.

Регистрация никогда не выдаёт роль сама: `role` всегда `'user'`, а панель проверяет роль на сервере при каждом запросе. Если войти без роли, форма покажет ваш публичный ID и напомнит про шаг с БД.

## SQL: выдача и отзыв роли

```bash
# 1. найти себя и посмотреть текущую роль
psql "$DATABASE_URL" -c "SELECT customer_no, email, role, status FROM site_users WHERE email = 'you@example.com';"

# 2. выдать роль
psql "$DATABASE_URL" -c "UPDATE site_users SET role = 'admin', status = 'active' WHERE email = 'you@example.com';"

# 3. войти на /admin и при необходимости обновить страницу
```

Отзыв роли действует на следующий запрос — активная сессия не сохраняет права:

```bash
psql "$DATABASE_URL" -c "UPDATE site_users SET role = 'user' WHERE email = 'you@example.com';"
```

Проверка состояния:

```bash
psql "$DATABASE_URL" -c "SELECT customer_no, email, role, status FROM site_users WHERE role = 'admin' ORDER BY customer_no;"
```

Роль хранится в `site_users.role` с ограничением `IN ('user','admin')`, статус — `IN ('active','banned')`.

## Публичный ID

У каждого аккаунта два идентификатора:

- `site_users.id` — случайный UUID, используется API и связями БД;
- `customer_no` → отображается как `LVK-000001` — для поддержки и поиска в панели.

Знание публичного ID не даёт доступа к данным: он не является ключом авторизации.

## Модель безопасности

Реализация опирается на:

- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) — deny by default, least privilege, проверка разрешений на каждом запросе, безопасный отказ;
- [OWASP A01 Broken Access Control](https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/) — скрытая кнопка не является защитой, все `/api/admin/*` идут через единый `requireAdmin`;
- [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) — действия и отказы журналируются, без паролей, токенов и credentials товаров;
- [OWASP Transaction Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) — значимые данные видны до подтверждения, каждое изменение требует повторного пароля и idempotency key.

Условия доступа к панели: действующая HttpOnly-сессия, `status = 'active'`, `role = 'admin'`, same-origin для изменений, rate limit, повторный текущий пароль для каждого действия. Отказ неавторизованного — 401, обычного пользователя — 403 и запись `authorization.denied` в `site_admin_audit`.

Бан удаляет все сессии цели, а центральный lookup сессии дополнительно исключает `status != 'active'`, поэтому украденная cookie не обходит блокировку. Email и Telegram-вход используют тот же запрет.

## Действия панели

- **Бан:** причина от 5 символов; нельзя забанить себя или другой admin-аккаунт; баланс и заказы сохраняются; все сессии отзываются.
- **Разбан:** возвращает возможность входа, старые сессии не восстанавливаются.
- **Начисление:** 1–50 000 ₽, атомарная транзакция с блокировкой кошелька, операцией `adjustment`, проводкой `admin_credit`. Повтор с тем же idempotency key не начисляет деньги дважды.
- **Выдать товар:** delivered-заказ с ценой 0 ₽. В demo — явно тестовый доступ; в live — атомарное резервирование записи `site_inventory`, иначе действие отклоняется. Credentials в audit не попадают.

## Управление продуктами

Раздел «Продукты» в `/admin`:

- **Убрать из продажи / Включить продажу** — мягкое скрытие (`products.is_active`). Скрытый продукт исчезает из каталога и Mini App, а checkout отклоняет его на сервере (`PRODUCT_NOT_FOUND`). Строка не удаляется: заказы и выданные доступы ссылаются на продукт и сохраняют историю.
- **Изменить цену** — от 1 до 1 000 000 ₽ в целых копейках. Запрос содержит цену, которую видел администратор (`expectedPriceCents`); если продукт успели изменить, правка отклоняется (`PRODUCT_CHANGED`), а не перезаписывает чужую. Checkout блокирует ту же строку и сверяет `expectedTotalCents`, поэтому покупатель с открытым окном оплаты не заплатит старую цену — он получит `PRICE_CHANGED` и подтвердит покупку заново.
- Каждое изменение требует текущего пароля администратора и пишется в журнал: `product.price_changed` (старая → новая цена), `product.enabled`, `product.disabled`.

Командные тарифы добавлены **выключенными**: `chatgpt-plus-4`, `chatgpt-plus-8`, `chatgpt-pro-4`, `chatgpt-pro-8`. Стартовые цены — 4 990 / 8 990 / 12 990 / 22 990 ₽ за 30 дней, их стоит проверить перед включением. Seed только добавляет отсутствующие slug и никогда не перезаписывает цену или видимость, изменённые в панели.

Подтверждение паролем блокируется после 5 **неверных** попыток за 15 минут; успешные действия лимит не расходуют, поэтому массовое редактирование каталога не упирается в блокировку.

Audit-таблица append-only: actor UUID, target UUID, action, безопасные details, время. Для production рекомендуется репликация в WORM/SIEM и alerting на частые `authorization.denied`, массовые баны и начисления.

## Длинный пароль вместо ролей: сравнение

Вариант «вход в панель по паролю из 512 символов» проигрывает ролевой модели:

- Пароль — это аутентификация, а не авторизация. Он отвечает на вопрос «кто ты», но не «что тебе разрешено». Права всё равно нужно где-то хранить и проверять.
- Такой пароль невозможно запомнить и неудобно вводить: его будут хранить в файле, чате или менеджере, копировать при каждом входе — это новый канал утечки.
- Длина не спасает от кражи сессии, фишинга, скомпрометированного браузера или утечки из логов: один секрет даёт полный доступ без ограничений и без журнала «кто именно».
- Отозвать доступ у одного человека нельзя, не поменяв пароль для всех.
- Нет разделения обязанностей: любой владелец секрета может и банить, и начислять деньги.

Ролевая модель лучше тем, что права привязаны к аккаунту, действия журналируются по конкретному оператору, доступ отзывается одной командой, а ошибки ограничены проверками (нельзя забанить админа, нельзя превысить лимиты).

**Что реально повышает защиту пароля:** длина 12–16+ у уникального пароля из менеджера, ограничение попыток входа, второй фактор (TOTP), повторный пароль для чувствительных действий, allowlist IP/VPN для `/admin`, журналирование и алерты.

**Где длинный случайный секрет уместен:** для машинных интеграций. Пример в проекте — `WALLET_ADMIN_SECRET` (минимум 32 символа) для сервер-сервер вызовов, где секрет не вводится человеком.

## Проверка

```bash
npx tsx scripts/test-admin.mts
npx tsx scripts/test-admin-browser.mts
```

Тесты сами регистрируют аккаунты, повышают роль через БД, проверяют вход, действия и отзыв роли, а после завершения удаляют свои данные. Постоянных админ-аккаунтов в коде и в базе нет.
