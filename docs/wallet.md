# LIVKAMARKET — кошелёк и покупки с баланса

## Что реализовано

Новый кабинет на `/`: баланс, быстрое пополнение, каталог, покупка с подтверждением, сохранённые доступы, история с фильтрами/пагинацией и CSV. `/miniapp` использует тот же балансный checkout. Старый `/api/order/pay` возвращает HTTP 410: TxID от пользователя больше не подтверждает оплату.

Средства, резервы и операции хранятся в PostgreSQL через Drizzle. Отдельные счета `(user_id, mode)` для демо и реальных денег. Суммы — целые копейки. Финансовые записи сериализованы блокировкой кошелька `SELECT ... FOR UPDATE` в транзакциях. У каждого действия уникальный idempotency key; проверяются и параметры повторного запроса. Журнал `site_wallet_entries` дополняется проводками; при отмене создаётся обратная проводка, а не удаляется списание.

## Текущий режим

При отсутствии `WALLET_MODE=live` включён **демонстрационный режим**, явно обозначенный в кабинете и денежных формах. Любое демо-пополнение, покупка и вывод не имеют реальной денежной стоимости. Заявки на демо-вывод можно создавать и отменять, но операторский API не может выплатить их. Демо-доступы явно обозначены и не активируют подписки. Переключение режима не переносит тестовый баланс в реальный.

## Исследование и принятые решения

1. [OWASP — Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html): значимые параметры видны перед подтверждением, проверяются на сервере, операция не может обойти последовательность состояний.
2. [OWASP — Secure Integration of Third-Party Payment Gateways](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Payment_Gateway_Integration_Cheat_Sheet.html): не доверять возврату браузера, TxID или неподписанному callback; проверять платёж сервер-сервер, валюту/сумму/ID; обеспечивать идемпотентность.
3. [Crypto Pay — официальная документация](https://help.send.tg/en/articles/10279948-crypto-pay-api): `createInvoice` с `currency_type=fiat`, `fiat=RUB`, `accepted_assets`; `getInvoices`; подпись HMAC-SHA256 raw body с ключом SHA256 API-токена, заголовок `crypto-pay-api-signature`.
4. [Drizzle — transactions](https://orm.drizzle.team/docs/transactions): транзакции, блокировка строки и откат всех связанных изменений.
5. [FATF — risk-based approach to virtual assets](https://www.fatf-gafi.org/content/dam/fatf-gafi/guidance/RBA-VA-VASPs.pdf): комиссия не заменяет идентификацию клиента, анализ транзакций, оценку риска и применимые требования законодательства. Реализованные ограничения — технические меры, не подтверждение AML-compliance и не юридическое заключение.

## Условия по умолчанию

- Пополнение: 100–50 000 ₽, комиссия сервиса 0%. Комиссия сети/провайдера, если есть, указывается у провайдера. Максимум 5 незавершённых счетов. Баланс + резервы + ожидаемые пополнения: максимум 1 000 000 ₽.
- Покупка: рублёвый баланс, комиссия 0%, промокоды проверяются на сервере. Если цена изменилась, пользователь должен заново подтвердить покупку. В live-режиме списание происходит только при наличии реального доступа на складе `site_inventory`.
- Вывод: от 1 000 ₽; 5% с округлением вверх до копейки, минимум 100 ₽; удерживается из указанной суммы. Суточный лимит 50 000 ₽ за скользящие 24 часа. Не более одной активной заявки.
- Реальный вывод: проверенный пользователь, пароль аккаунта, 24 часа после пополнения, контрольная сумма USDT/TRC-20 адреса, ручной review. Сумма в RUB фиксирована; итоговый эквивалент USDT согласуется с владельцем до реального перевода. Внешняя выплата выполняется оператором, а не автоматически этой системой.
- Статусы вывода: pending → processing → completed / rejected. Из pending пользователь может отменить. При отмене/отклонении возвращается вся сумма, включая резерв комиссии. После начала обработки пользователь не может отменить уже выполняемый перевод.
- Демо-режим не требует настоящей проверки личности и ожидания 24 часов, поскольку не оперирует реальными средствами.

Изменение условий: `src/lib/wallet-shared.ts`. Изменения тарифов необходимо синхронизировать с публичными текстами и юридическими условиями.

## Подключение live

Настройки задаются только на сервере (не NEXT_PUBLIC):

- `WALLET_MODE=live`
- `CRYPTO_PAY_API_TOKEN` — токен production-приложения в @CryptoBot. Используется только фиксированный HTTPS endpoint https://pay.crypt.bot/api; тестовый endpoint намеренно не используется для live-счёта.
- `WALLET_ADMIN_SECRET` — случайный секрет минимум 32 символа для оператора; хранить в secret manager.
- `DATABASE_URL` — PostgreSQL URL.

Зарегистрировать HTTPS webhook: `https://<домен>/api/wallet/webhook`. Разрешить invoice_paid и проверить реальным малым платежом. Подпись проверяется constant-time, затем сервер независимо вызывает getInvoices и сверяет invoice_id, payload (наш operation ID), сумму, валюту, статус. Кнопка «Проверить платёж» делает ту же серверную проверку. Не оплаченный/неподтверждённый счёт не увеличивает баланс. Истёкший счёт при проверке получает статус expired.

**До приёма реальных средств:** заполнить настоящий склад, организовать операторскую поддержку, KYC/AML-процедуру, sanctions/transaction screening через подходящего провайдера, согласовать применимые юридические условия, возвраты и хранение денег, проверить разрешение Crypto Pay для этого бизнеса/юрисдикции, настроить мониторинг webhook и сверку проводок/платёжного провайдера. Автоматический screening/KYC-провайдер в этом проекте не подключён. Пароли/доступы на складе требуют защищённого хранения БД, ограниченных ролей и шифрования диска/бэкапов.

## Операторский API

`Authorization: Bearer <WALLET_ADMIN_SECRET>`, секрет не передавать браузеру. Доступ желательно ограничить сетью/прокси. Каждый POST требует `actor` (идентификатор оператора), действия записываются в `site_wallet_audit`. Секрет сравнивается constant-time; при отсутствии/слабом секрете доступ закрыт.

- `GET /api/internal/wallet`: очередь реальных pending/processing заявок и статус проверки владельца.
- `POST /api/internal/wallet`, action=`verify-wallet`, walletId (UUID), status=`verified|unverified|blocked`, reference (не менее 8 символов), actor. Статус verified выставлять только ПОСЛЕ настоящей проверки личности/риска. reference — ID кейса у провайдера, не скан документа.
- action=`review-withdrawal`, operationId, status=`processing`, reference (ID review-кейса), actor. Перед реальным переводом обязательно захватить заявку переводом в processing — это запрещает отмену пользователем.
- action=`review-withdrawal`, operationId, status=`completed`, reference (реальный TRON tx hash, 64 hex), actor. Только после внешней проверки успешно отправленной суммы и адреса. API фиксирует факт ручной выплаты, но сам не проверяет блокчейн и не отправляет средства.
- action=`review-withdrawal`, operationId, status=`rejected`, reference (причина), actor — освобождение резерва. Отклонять только если внешняя выплата не совершена.
- action=`inventory-add`, productId, credentials (строка с настоящими данными доступа), actor. Запись склада атомарно привязывается к оплаченному заказу. Не загружать один и тот же доступ повторно.

## Запуск и проверки

`npx drizzle-kit push` применяет таблицы. Схема не удаляет прежние заказы и пользователей. Каталог автоматически заполняется из существующего seed при первом открытии.

Обязательная валидация: `npx next typegen`, `npm exec tsc -- --noEmit --pretty false`, `npm run build`.

`npx tsx scripts/test-wallet.mts` (после запуска приложения) выполняет HTTP-интеграционные тесты только в demo-режиме, включая race/replay, баланс, журнал проводок, отмену, IDOR и отключение старого endpoint. Тестовые аккаунты и их данные удаляются после теста. `TEST_BASE_URL` по умолчанию http://localhost:3000.
